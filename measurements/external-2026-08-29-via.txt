PARAMETERS CHANGED FROM SHIPPED: src/core.hpp LOG_COL 13 -> 9.
  Shipped LOG_ROW=8, LOG_COL=13 allocates ROW*COL = 2^21 polynomials of
  DEGREE1=2048 uint64 = 32 GiB of NTT coefficients for a 4 GiB logical
  database.  That is 8x expansion and it OOM-kills (rc=137) on this
  16 GB machine.  LOG_COL=9 gives a 256 MB database and a 2.1 GB
  allocation, which fits.  core.hpp was restored after the build.
  The authors' own machine is a Ryzen 9 9950X with 128 GB (README).

READ THE FIRST DIMENSION NUMBER WITH CARE.  In src/VIAServer.hpp the
  First Dimension loop runs the full COL x ROW iteration count but every
  operand is literal index 0 -- database[0], FirstDimVec[0],
  FirstDimResMasks[0].  The loop counters i and j index nothing.  The
  operation count is right; the memory traffic is not, because one 16 KB
  polynomial is re-read instead of the database being streamed.  The
  README discloses this for databases above the allocation cap ('the
  First Dimension operations will simulate memory usage for the full
  database'); the code applies it unconditionally, at every size.
  src/VIA_CServer.hpp does the same in its First Dimension loop.

The harness does not check that the right record came back.  test.cpp
  calls client.Recover(ans, result) and never compares result to
  anything.  This repository gates every printed timing on a
  correctness check (ADR 0002 point 6); VIA's does not.
